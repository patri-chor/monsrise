# T052 - Unified Hill-Climb and Conditional-Branch Learning

> Merge local hill-climb optimization and conditional branch induction into one product-path search loop. A local solution that improves a targeted matchup but regresses the global pool must not be discarded automatically; it becomes a branch candidate when its gain is attributable to an observable opponent label. A branch candidate must also be locally optimized and tested for safe forward movement to the earliest legal information round.

## A. Current Gap Confirmed

Current systems are only loosely related:

```text
hill_climb.ts:
  mutates whole EvolFormation, including random addBranch
  evaluates weakest arena score
  accepts/rejects whole candidate
  has no failure-to-conditional-branch handoff

branch_induct.ts:
  observes labels/branch decisions and can add/optimize branches
  uses a separate induction flow
  has no reliable intake of hill-climb local improvements rejected by global regression

product_tree_strategy:
  selects already-existing branches from visible labels
  does not automatically explain rejected local improvements as branches
```

Do not treat the random `addBranch` mutation inside hill climb as this integration. The missing behavior is explicit local-gain attribution and routing.

## B. Unified Candidate Routing Model

For every local candidate generated by spatial/order/badge/calculator/tree mutation:

```text
1. Evaluate parent and candidate on the same product-path panel.
2. Preserve raw W/D/L by opponent, side, label, round, seed and branch decision.
3. Compute Score70 = (W + 0.70D) / N, WinRate, DrawRate, LossRate.
4. Evaluate both:
   - global panel delta
   - targeted label-subset delta
5. Route candidate:

GLOBAL_IMPROVEMENT:
  candidate may replace/advance the main parent if global regression gates pass.

LOCAL_ONLY_IMPROVEMENT:
  global score regresses or is neutral, but one or more observable label subsets
  improve with sufficient coverage and no unacceptable regression inside that subset.
  Convert the local solution into a conditional branch candidate.

NO_INFORMATIVE_GAIN:
  neither global nor label-local improvement; retain as rejected experiment.

INVALID:
  provenance, visibility, product validation, arithmetic, or leakage failure.
```

A local improvement must not be promoted merely because one opponent was beaten once. Require configurable minimum coverage per label/side and fresh seeds; record the exact thresholds and sample counts.

## C. Label Attribution From Real Product Games

The product-path run must retain enough observations to attribute each game to labels actually visible at the proposed fork:

```text
R1:
  enemy revealed hand IDs/badges only

R2+:
  R1 visibility plus currently revealed enemy board IDs
```

For each candidate game and possible fork round, record:

```text
recognized main/sub/key labels
visible feature inputs
selected branch ID or main fallback
branch/fork round
W/D/L outcome
Score70 contribution
```

Do not infer hidden future labels. If `mine` or `fullrush` is not visible at a fork, that game cannot support a branch condition at that fork.

Use complete W/D/L outcome metrics. Do not discard draws or reduce induction to a win/loss-only entropy calculation.

## D. Local Solution -> Branch Conversion

When a local candidate improves a label subset but regresses the global panel:

```text
1. Identify the smallest observable FeatureMask explaining the gain:
   side, main, subs, keys, or approved conjunction.
2. Copy only the local candidate's changed subtree/placements/calculator policy
   into a branch variant; preserve the parent main branch unchanged.
3. Attach the condition at a legal fork node.
4. Record conversion metadata:
   parent fingerprint
   local candidate fingerprint
   condition mask
   target label subset
   global W/D/L delta
   local W/D/L delta
   Score70 deltas
   affected rounds/nodes
   operator family and seed
   conversion reason
5. Validate branch tree, R1/R2 visibility, duplicate/collision/budget rules.
```

The branch must be behaviorally distinct. A no-op or fingerprint-equivalent branch is rejected.

Keep branch candidates separate from main candidates in lineage and evidence. A local branch success must not be misreported as a global formation improvement.

## E. Branch-Local Optimization

After conversion, run a focused hill climb over the branch subtree only:

```text
allowed:
  placement/order/badge/calculator-policy/tree changes within branch scope
  branch condition refinement when supported by visible observations

forbidden:
  mutation of unrelated main branch
  mutation of R0 historical roots
  hidden context access
  generic BattleAI/arena evidence
```

Use product-path evaluations. Accept a branch-local mutation only when it improves the target label subset under Score70/WDL and does not violate the branch's global safety budget. Preserve the best local branch variant and its rejected alternatives for audit.

## F. Forward-Node Mechanism

Add explicit `forwardBranchCandidate` evaluation; `addBranch(targetRound)` alone is not sufficient.

For a branch first discovered at round R:

```text
try candidate fork rounds R-1, R-2, ..., R1
only if the condition is observable at the earlier round
for each earlier fork:
  replay the same branch solution from that fork
  evaluate product-path W/D/L and label coverage
  check early placement/budget side effects
```

Accept the earliest round only if:

```text
condition is legally visible there
branch-local Score70 gain remains positive or within configured tolerance
main-branch/global safety regression is within configured bound
no early budget/collision/duplicate violation
P1/P2 and fresh seed coverage pass
```

If earlier placement changes are harmful, retain the later fork and record why forwarding was rejected. Do not assume earlier is better.

## G. Scoring and Regression Policy

Use the current dynamic metric revision:

```text
primary Score70 = (W + 0.70D) / N
retain WinRate/DrawRate/LossRate and legacy Score50 for audit
```

All candidate routing records must bind:

```text
formation/tree fingerprint
calculator policy fingerprint
benchmark/Active-L2 manifest revision
L1 manifest where applicable
seed schedule
product-path provenance
```

Global and local gates must be explicit and revisioned. Do not use old `weakest adScore` or arena scores as current acceptance evidence. A candidate may be globally worse and locally valuable only through the LOCAL_ONLY_IMPROVEMENT path; it may not change current T-tier by itself.

## H. Candidate Queue and Search Integration

Create a unified result type, for example:

```ts

  | { route: 'GLOBAL_IMPROVEMENT'; candidate: ... }
  | { route: 'LOCAL_ONLY_BRANCH'; branchCandidate: ... }
  | { route: 'NO_INFORMATIVE_GAIN'; ... }
```

Use one shared candidate/evidence queue for:

```text

```

Do not merge records with identical display IDs but different tree/policy fingerprints.
